## 1. 概要

本システムは、Discordを主要な操作窓口として、利用者ごとの対話、要点整理、タスク管理、メール補助、PDF出力を行う業務支援Botである。

各利用者は専用の対話窓口を持ち、その窓口内で相談・指示・確認を行う。  
会話内容は必要に応じて整理・構造化され、Trello や Gmail などの外部ツールと連携される。

また、本システムは OpenAI API を活用し、会話内容の要約、タスク抽出、決定事項抽出、重要リンク整理、文面生成を行うことを前提とする。  
これにより、Discord上の対話を単なるログではなく、再利用可能な業務情報として扱う。

---

## 2. 目的

### 2.1 主目的
1. Discord上の会話が流れて埋もれる問題を軽減する
2. 会話内容をタスク・決定事項・重要リンクとして再利用可能にする
3. 対話結果や整理結果をPDFとして保存・共有可能にする
4. Discordから外部ツールを操作可能にする
5. 外部ツール側の更新内容もDiscordから閲覧可能にする
6. OpenAI API を利用して、会話内容の要約・抽出・生成を自動化する

### 2.2 想定利用シーン
- 利用者ごとの相談窓口運用
- 案件単位の進捗管理
- Discord上の会話からのタスク起票
- 相談結果のPDF保存
- GmailやTrelloを含む業務導線の集約
- OpenAI API による会話整理・文面生成

---

## 3. システム構成

### 3.1 基本構成
- **Discord**  
  利用者との対話窓口、コマンド操作画面
- **業務ハブAPI / Pythonアプリ**  
  コマンド処理、要約処理、外部連携処理の中核
- **OpenAI API**  
  会話内容の要約、タスク抽出、決定事項抽出、重要リンク整理、文面生成を担当
- **Database**  
  利用者、窓口、要点、タスク、決定事項、外部連携ID等を保存
- **Connector群**  
  Trello、Gmail、将来的な他ツール連携
- **PDF生成機能**  
  対話結果や整理結果をPDF化する機能

### 3.2 設計原則
- Discordを入口として統一する
- データの正本は中央ハブで持つ
- OpenAI API を整理・生成処理の頭脳として利用する
- 外部ツールは connector 方式で追加する
- 利用者ごとの窓口を分離して扱う
- 会話ログと整理済みデータを分離して管理する

## 4. Discord構成方針

### 4.1 窓口方式
以下のいずれかを採用する。

#### 方式A: 利用者ごとの専用チャンネル
- 少人数向け
- 視認性が高い
- チャンネル数増加に注意

#### 方式B: 受付チャンネル配下の専用 private thread
- 中規模以上向け
- 推奨方式
- 利用者単位で整理しやすい

### 4.2 推奨チャンネル構成
- `#窓口-受付`
- `#bot-commands`
- `#daily-summary`
- `#決定事項`
- `#重要リンク`
- `#運営ログ`
- `#障害通知`

### 4.3 窓口要件
各窓口は以下を満たすこと。

- 利用者本人がアクセス可能
- 運営が必要に応じてアクセス可能
- Botが投稿・添付・参照・処理実行可能
- 窓口単位で会話コンテキストを保持可能
- 窓口内で PDF 出力、要約、タスク化が可能

## 6. Slash Command 仕様

### 6.1 窓口管理系

#### `/session-open`
利用者専用の窓口を作成する、または現在のチャンネルでセッションを開始する。

#### `/session-close`
窓口を終了状態にする。

#### `/session-clear`
Botが保持している現在窓口の作業用コンテキストをクリアする。

---

### 6.2 整理・出力系

#### `/summary-today`
当日分のやり取りを整理し、要点・タスク・決定事項を出力する。

#### `/pdf-export`
現在の窓口における対話結果または整理結果をPDFとして出力する。

#### `/link-save`
重要リンクを保存する。

#### `/decision-add`
決定事項を保存する。

---

### 6.3 タスク管理系

#### `/task-add`
タスクを追加する。

主な入力項目例:
- タイトル
- 説明
- 担当者
- 期限
- 優先度

#### `/task-list`
現在の窓口または利用者に紐づくタスク一覧を表示する。

#### `/task-move`
タスクの状態を変更する。

状態例:
- `TODO`
- `DOING`
- `WAITING`
- `DONE`
- `ARCHIVED`

#### `/task-done`
対象タスクを完了状態にする。

---

### 6.4 Gmail連携系

#### `/mail-draft`
Gmailにメール下書きを作成する。

主な入力項目例:
- 宛先
- 件名
- 本文
- CC
- BCC

#### `/mail-send`
承認済み下書きを送信する。

---

### 6.5 Trello連携系

#### `/trello-add`
Trelloにカードを作成する。

#### `/trello-move`
Trelloカードを別リストへ移動する。

#### `/trello-comment`
Trelloカードにコメントを追加する。

## 7. 外部連携仕様

### 7.1 共通方針
外部ツール連携は connector 方式とする。  
各ツールの責務を分離し、中央ハブを経由して同期する。

### 7.2 各connectorの責務
- 変更取得
- 操作反映
- イベント正規化
- 内部IDとの紐付け
- エラー通知
- 疎通確認

### 7.3 Trello連携
- Discordからカード作成
- Discordから状態変更
- Discordからコメント追加
- Trello側更新のDiscord反映

### 7.4 Gmail連携
- Discordから下書き作成
- Discordから送信
- Gmailスレッド参照
- Gmail側更新の取り込み
- 将来的なラベルベース起票

### 7.5 OpenAI連携
OpenAI API に関しては以下を実現対象とする。

- 会話内容の要約
- タスク候補抽出
- 決定事項抽出
- 重要リンク整理
- Gmail下書き文面生成
- PDF用出力文面生成

OpenAI API は、Discord上の対話内容を再利用可能な構造へ変換するための中核ロジックとして利用する。

### 7.6 将来拡張候補
- Notion
- Google Calendar
- Google Drive
- GitHub
- スプレッドシート

## 12. 双方向同期仕様

### 12.1 基本方針
Discord、Trello、Gmailなど複数ツール間の操作は中央ハブを経由して同期する。

### 12.2 目的
- どのツールから操作しても結果を集約する
- 片側のみ更新による断絶を防ぐ
- Discordから外部状態を確認できるようにする

### 12.3 同期対象例
- Task状態
- メール下書き・送信履歴
- Trelloカード情報
- 関連リンク
- 更新日時

### 12.4 設計上の留意点
- 内部IDを中心に紐付ける
- 外部ツールごとの主キーを保持する
- 競合解決ルールを明文化する
- 同期失敗時はエラー通知と再試行を設計する

## 13. 非機能要件

### 13.1 拡張性
- 新しい外部ツールを connector 追加で実装できること
- Discord側の操作体系を大きく変えずに機能追加できること

### 13.2 保守性
- コマンド処理、連携処理、保存処理を分離すること
- ログを追いやすいこと
- 障害箇所の切り分けが可能であること

### 13.3 セキュリティ
- 権限に応じた操作制御
- 利用者ごとの窓口隔離
- 外部ツール認証情報の安全な保管
- 監査ログの保持
- OpenAI API キーの安全な保管
- APIキーを .env 等で管理し、リポジトリへ含めないこと
- 外部API利用時のログ出力に秘密情報を含めないこと

### 13.4 可用性
- 日常利用に耐える安定動作
- 外部ツール障害時も窓口機能自体は継続利用可能であること
- 障害時に通知可能であること

### 13.5 監査性
- 主要操作の監査ログを残す
- 外部連携実行履歴を追跡可能とする

## 15. 想定運用フロー

### 15.1 基本フロー
1. 利用者が窓口を開く
2. 窓口内で相談・依頼・確認を行う
3. OpenAI API を利用して要約、タスク候補、決定事項候補を整理する
4. 必要に応じて確定情報として保存する
5. 外部ツールへ反映する
6. 必要に応じて PDF 出力する
7. 作業終了後、窓口を終了する

### 15.2 タスク起票フロー
1. 利用者が Discord で内容を相談
2. OpenAI API によりタスク候補を抽出
3. `/task-add` を実行
4. 内部タスク作成
5. Trello へ反映
6. 結果を Discord に返却

### 15.3 メール作成フロー
1. 利用者が `/mail-draft` を実行
2. OpenAI API が文面案を生成
3. 下書き作成
4. 下書き情報を内部保存
5. 必要に応じて `/mail-send` で送信

### 15.4 PDF出力フロー
1. 利用者が `/pdf-export` を実行
2. 窓口情報を収集
3. 必要に応じて OpenAI API で本文整形
4. PDF生成
5. 窓口に返却
6. 履歴保存
